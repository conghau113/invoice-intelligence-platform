# T1.1 — Ghi chú cổng hiểu (Keycloak realm-as-code)

## 1. Keycloak là gì, realm/client/role/organization

**Câu hỏi:** Keycloak là gì và giải quyết vấn đề gì trong hệ thống? Realm, client, role, organization là gì? Thiếu Keycloak thì phần nào thiếu hoặc phải tự làm?

**Trả lời:**
- **Keycloak** là IdP self-host: quản lý user, đăng nhập OIDC, cấp JWT. App không tự lưu mật khẩu hay tự phát token. Nó trả lời "ai đang gọi" và "thuộc tenant nào, role gì", miễn phí và đúng chuẩn enterprise (ADR 0005).
- **Realm**: không gian cô lập cấu hình (user, client, role). Dự án dùng một realm `invoice` cho mọi tenant.
- **Client**: ứng dụng được phép xin token. Có `web` (confidential, PKCE, dùng cho BFF), `api` (bearer-only, chỉ làm audience, không đăng nhập) và `dev-cli` (chỉ dev, lấy token bằng curl).
- **Role**: nhãn quyền (`tenant_admin`, `accountant`, `viewer`) là realm role; API map sang permission.
- **Organization**: nhóm B2B trong realm, một organization là một tenant; claim `organization` trong access token cho API biết tenant.
- Thiếu Keycloak: phải tự làm đăng nhập, mật khẩu, session, phát và xác minh token, và mô hình "user thuộc công ty nào". Nhưng RLS và RBAC vẫn là việc của Postgres và Nest; Keycloak chỉ cho claim tin cậy để chúng bám vào.

**Lưu ý:**
- `api` là client bearer-only: nó không xin token, chỉ để token của `web` mang `aud: api` nhờ audience mapper; API dùng đó để từ chối token cấp cho nơi khác.
- Role là realm role, không theo organization: user thuộc hai tenant có cùng role ở cả hai (Phát sinh cho T1.4).
- Claim `organization` phụ thuộc scope xin lúc đăng nhập. Cấu hình mapper đúng chưa đủ.

## 2. Luồng từ "Đăng nhập" đến API trả đúng tenant

**Câu hỏi:** Kể end to end từ lúc bấm "Đăng nhập" đến lúc API trả dữ liệu đúng tenant. Ai làm gì, token nào được cấp, API tin token thế nào mà không hỏi Keycloak mỗi request?

**Trả lời:**
1. Trình duyệt tới web/BFF, chưa có session.
2. BFF bắt đầu Authorization Code + PKCE, chuyển trình duyệt sang Keycloak, xin scope `openid organization:*`.
3. User đăng nhập ở Keycloak, được chuyển về callback của BFF kèm authorization code.
4. BFF (phía server) đổi code cùng `code_verifier` lấy access token, refresh token và ID token. Chúng nằm trong session mã hóa; trình duyệt chỉ nhận cookie httpOnly, Secure, SameSite.
5. Khi cần dữ liệu, server Next gọi Nest với `Authorization: Bearer <access token>`.
6. API kiểm chữ ký bằng JWKS đã cache, rồi kiểm `iss`, `aud`, `exp`, `nbf`. Không hỏi Keycloak mỗi request.
7. Tenant lấy từ claim `organization` (đã xác minh), role map sang permission, rồi đặt tenant cho RLS trong transaction.
8. Access token hết hạn thì BFF dùng refresh token; refresh lỗi thì kết thúc phiên.

**Lưu ý:**
- JWT mang `kid`. Gặp `kid` chưa có trong cache thì API tải lại JWKS (có giới hạn tần suất), không chỉ chờ cache hết hạn. Đó là cách xử lý rotation khóa (câu hỏi ở T1.2).
- Đặt tenant bằng `set_config('app.tenant_id', $1, true)` trong transaction, không dùng `SET` thường; tham số `true` làm giá trị chỉ sống đến hết transaction nên không rò sang request khác trên cùng connection pool.
- Header tenant không bao giờ là nguồn tin cậy. T1.2 lấy tenant từ claim; T1.7 nhận tenant đã chọn nhưng kiểm membership.
- Thiếu scope `organization:*` thì user nhiều tenant không có claim, và API phải từ chối chứ không đoán tenant.
- ID token còn dùng làm `id_token_hint` khi gọi end-session lúc đăng xuất.

## 3. Đánh đổi: một realm + Organizations

**Câu hỏi:** Vì sao chọn một realm với Organizations thay vì realm riêng mỗi tenant hay Auth0/Clerk? Cái giá là gì, và khi nào quyết định này sai, thấy dấu hiệu gì?

**Trả lời:**
- **Lý do chọn:** thêm tenant là thêm dữ liệu chứ không phải thêm hạ tầng; một issuer và một JWKS cho API; miễn phí; câu chuyện enterprise tự host IdP.
- **Cái giá:**
  - Keycloak tốn khoảng 0.75-1 GB RAM trên VM demo dùng chung.
  - Organizations không tự động: user nhiều tenant cần scope `organization:*`; claim là alias nên phải ánh xạ sang `tenant_id` uuid; role theo realm không theo tenant.
  - Phải tự vận hành: import realm, `IGNORE_EXISTING`, issuer phụ thuộc host.
  - Cách ly ở tầng IdP yếu hơn realm-per-tenant.
- **Khi nào sai, dấu hiệu:**
  - Cần quyền khác nhau theo từng tenant (admin ở A, viewer ở B): realm role không biểu diễn được.
  - Claim hoặc scope Organizations khó dùng ở BFF: login được nhưng API trả "không có tenant" hàng loạt.
  - VM demo hết RAM: Keycloak restart, health/ready đỏ.
  - Khách yêu cầu cách ly IdP hoặc branding riêng.
  - Khi đó mở lại ADR 0005 và xét realm-per-tenant hoặc IdP managed.

**Lưu ý:**
- Auth0/Clerk có gói free; lý do loại không chỉ là tiền mà còn vendor lock-in và quy tắc không thêm dịch vụ ngoài khi chưa duyệt.
- Điểm mạnh thật của realm-per-tenant ngoài `iss` khác nhau: khóa ký tách riêng nên lộ hay rotate khóa chỉ ảnh hưởng một tenant.
- Client `dev-cli` và mật khẩu demo phải gỡ trước production (T4.7); chưa có gate nào ép việc này.
