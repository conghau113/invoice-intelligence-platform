# T1.5 — Gate notes: đăng nhập Keycloak qua BFF, session, refresh token

## Câu 1 — BFF, XSS và CSRF

**Câu hỏi:** BFF là gì và giải quyết vấn đề gì trong hệ thống này? XSS và CSRF khác nhau thế nào? Token trong localStorage mở ra tấn công nào, cookie httpOnly chặn được và không chặn được gì?

**Trả lời:** BFF (Backend-for-Frontend) là lớp server của web (Next.js + Auth.js) đứng giữa trình duyệt và Keycloak/API. Đăng nhập OIDC chạy ở server, access/refresh token nằm trong cookie session mã hoá, httpOnly; trình duyệt chỉ giữ cookie, server gắn Bearer khi gọi API. XSS là chạy JS độc trong trang của mình; CSRF là lừa trình duyệt đã đăng nhập tự gửi request tới site mình. Token trong localStorage thì mọi script trên trang đọc được, nên XSS lấy được token và dùng ở bất cứ đâu. Cookie httpOnly khiến JS không đọc được token, nên XSS không "mang token đi" được. Đổi lại, cookie được trình duyệt tự gắn vào request nên có nguy cơ CSRF; giảm bằng SameSite=Lax, thao tác đổi trạng thái dùng POST, và logout kiểm Origin. API vẫn tự kiểm JWT và quyền.

**Lưu ý:**
- httpOnly không vô hiệu hoá XSS: script độc vẫn chạy trong trang và gọi `fetch` thì trình duyệt tự gắn cookie, nên kẻ tấn công vẫn hành động nhân danh user khi trang còn mở. BFF chỉ thu nhỏ thiệt hại (không lấy được refresh token sống lâu mang đi).
- Hai tấn công đối ngược: token ở localStorage gửi bằng header `Authorization` thì không bị CSRF nhưng dễ bị XSS; cookie thì ngược lại. Chọn cookie là đổi rủi ro, không xoá rủi ro.
- SameSite=Lax vẫn gửi cookie khi điều hướng cấp cao nhất bằng GET (bấm link), nên không được dùng GET cho thao tác đổi trạng thái. Logout là POST + kiểm Origin vì lý do này.

## Câu 2 — Refresh token và rotation

**Câu hỏi:** Khi access token (5 phút) sắp hết hạn, hệ thống làm gì để người dùng không phải đăng nhập lại, và ai làm bước nào? "Rotation" nghĩa là gì, điều gì xảy ra nếu một refresh token dùng hai lần? Refresh thất bại thì người dùng thấy gì?

**Trả lời:** Trình duyệt chỉ gửi cookie. Proxy (chạy trước khi render) đọc cookie, thấy access token còn dưới 60 giây thì gọi Keycloak `grant_type=refresh_token` từ server. Keycloak trả access token mới và refresh token mới, đồng thời thu hồi refresh token cũ (rotation). Proxy mã hoá lại và ghi cookie mới, và chuyển cookie mới cho trang đang render, rồi cho request đi tiếp; người dùng không thấy gì. Dùng lại refresh token đã dùng thì Keycloak từ chối (`invalid_grant`), app coi là phiên không còn tin được: xoá cookie, về `/login`. Nếu Keycloak lỗi tạm (5xx, timeout, mạng) thì giữ phiên, không xoá cookie, lần sau thử lại; chỉ khi bị từ chối (400/401) mới đăng xuất.

**Lưu ý:**
- Refresh nằm ở proxy chứ không ở Server Component vì Server Component không ghi được cookie: refresh xong mà không lưu được thì lần sau dùng lại token cũ đã bị thu hồi và người dùng bị văng. Bản đầu của agent còn đường refresh trong callback `jwt`, code-review phát hiện và đã bỏ.
- Single-flight cần vì rotation chỉ cho dùng token một lần: hai request song song cùng mang token cũ thì request thứ hai nhận `invalid_grant` và người dùng bị đăng xuất oan.
- Single-flight chưa đủ: request đã gửi trước khi trình duyệt nhận cookie mới có thể đến sau khi refresh xong và vẫn mang token cũ. Bản đầu của agent bỏ sót; sửa bằng cách nhớ kết quả 30 giây theo token cũ.
- Mục đích của việc chặn dùng lại là phát hiện token bị đánh cắp (hai bên cùng cầm một token thì một bên bị từ chối). Keycloak có thể huỷ cả phiên SSO khi thấy dùng lại; chưa kiểm chứng trong dự án.
- Ở trạng thái "Keycloak lỗi tạm", trang vẫn vào được nhưng gọi API với access token hết hạn sẽ 401. Đó là chủ ý.

## Câu 3 — Cookie JWT không trạng thái và phương án session phía server

**Câu hỏi:** So sánh session JWT mã hoá nằm trong cookie (đang dùng) với session phía server (cookie chỉ chứa session id, token ở Redis/DB): được gì, mất gì, vì sao chọn cách hiện tại và khi nào đổi?

**Trả lời:** Cookie JWT: không cần store session, scale ngang dễ, Auth.js hỗ trợ sẵn, hợp ADR 0006 cho giai đoạn đầu. Điểm yếu thật: cookie to (đang ~4.7KB, đã phải chia 2 mảnh; thêm claim thì chạm giới hạn trình duyệt); logout chỉ xoá cookie ở trình duyệt, bản cookie cũ vẫn dùng được đến khi access token hết hạn (≤5 phút) rồi refresh mới thất bại; single-flight chỉ đúng trong một process nên nhiều instance sẽ lại gặp race refresh. Session phía server: revoke tức thì bằng cách xoá bản ghi, cookie nhỏ, chia sẻ trạng thái refresh giữa các instance; đổi lại thêm Redis/DB (một điểm lỗi, độ trễ mỗi request, vận hành), và vẫn phải bảo vệ session id. Chọn cookie JWT giờ vì ít thành phần, vài instance, access token ngắn giới hạn cửa sổ replay. Cân nhắc đổi khi chạy nhiều replica, cookie quá to, cần revoke tức thì ("đăng xuất mọi nơi"), hoặc replay thành vấn đề bảo mật thực sự.

**Lưu ý:**
- Cookie JWT chứa cả refresh token, nên lộ cookie (hoặc `NEXTAUTH_SECRET`) nghiêm trọng hơn lộ một session id trần.
- Sau logout, Keycloak đã kết thúc phiên SSO nên cookie cũ không refresh được; cửa sổ replay chỉ còn bằng thời gian sống của access token.
- Những điểm này đã nằm trong "Phát sinh" của `TASKS.md` (replay sau logout, nhiều instance, kích thước cookie) để xử lý ở M8 / security review.
