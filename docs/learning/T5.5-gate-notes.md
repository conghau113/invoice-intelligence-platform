# T5.5: cổng hiểu (Server-Sent Events, streaming UI)

## Câu 1: SSE là gì, vai trò trong màn hỏi đáp

**Câu hỏi**

Server-Sent Events (SSE) là gì? Trong màn hỏi đáp của hệ thống này, SSE giải quyết vấn đề gì? Nếu web gọi `/qa/ask` như một request JSON thông thường, chờ trả về một cục rồi mới hiển thị, thì người dùng mất gì và hệ thống mất gì?

**Trả lời**

SSE là một response HTTP bình thường với `Content-Type: text/event-stream`. Server không đóng kết nối mà ghi lần lượt từng event (`event:`, `data:`, rồi một dòng trống). Dữ liệu chỉ đi một chiều, từ server xuống, và vẫn đi qua cookie, proxy, BFF như mọi request khác.

Ở đây, API trả về một chuỗi event có cấu trúc: `token`… (chữ của câu trả lời) hoặc `aggregate` (số liệu do SQL tính), sau đó là `citations`, hoặc chỉ một `refusal`; luôn kết thúc bằng `done`. Đây là hợp đồng giữa API và web, và mọi event đều được kiểm bằng schema dùng chung.

Điểm phải nói rõ: T5.4 chọn "kiểm xong mới phát". API phân loại, truy hồi, gọi model và kiểm trích dẫn xong hết rồi mới ghi byte đầu tiên. Vì vậy, hiện tại SSE **chưa** cho phản hồi sớm thật sự:
- Khoảng chờ dài vẫn y như khi dùng JSON. Trạng thái "đang tìm…" do web tự hiện ngay lúc bấm Hỏi.
- Token tới gần như cùng lúc.

Giá trị của SSE lúc này là định dạng event. Khi nào API chuyển sang stream token thật (phải giải được bài kiểm trích dẫn giữa chừng), web không phải sửa gì.

So với JSON một cục, người dùng gần như không mất gì ở thời điểm hiện tại. Thứ mất đi là đường nâng cấp lên streaming thật mà không phải đổi hợp đồng.

**Lưu ý**

- Nút Dừng không phải ưu điểm riêng của SSE. Request JSON cũng huỷ được bằng `AbortController`: đóng kết nối thì API thấy socket đóng và huỷ lời gọi model.
- SSE không giúp gì cho quãng im lặng trước byte đầu tiên; vẫn cần timeout (BFF dùng 90 giây). SSE còn có thêm một rủi ro mà JSON không có: proxy nén (gzip) có thể gom event tới cuối. Vì vậy API và BFF gửi `Cache-Control: no-transform`.

## Câu 2: Từ lúc bấm Hỏi tới khi có chip trích dẫn, và đường đi của nút Dừng

**Câu hỏi**

Kể lại từ lúc người dùng bấm **Hỏi** tới lúc màn hình có câu trả lời với chip trích dẫn bấm được: trình duyệt, BFF Next.js và API mỗi bên làm gì? Vì sao trình duyệt không dùng `EventSource` có sẵn? Trình duyệt biến luồng byte thành từng event thế nào? Khi bấm **Dừng**, tín hiệu huỷ đi qua những chặng nào?

**Trả lời**

1. **Trình duyệt** `fetch` POST `/api/qa/ask` (cùng origin, kèm cookie phiên, body `{question}`).
   - Không dùng `EventSource` vì nó chỉ hỗ trợ GET. Câu hỏi sẽ phải nằm trong URL, mà URL thì lọt vào access log, lịch sử trình duyệt và header `Referer`; câu hỏi có thể chứa tên hay số tiền.
2. **BFF** kiểm request cùng origin (chống CSRF, vì xác thực bằng cookie), body là JSON với độ dài hợp lệ, và phiên có token. Sau đó BFF gắn bearer token và tenant rồi chuyển body lên API. BFF **không** kiểm quyền: quyền `qa:ask` và tenant do API kiểm trên token đã ký.
3. **API** phân loại, truy hồi hoặc chạy SQL, gọi model, kiểm trích dẫn, rồi mới ghi các event SSE.
4. **BFF** trả `upstream.body` thẳng xuống trình duyệt: không đọc, không gom, không log.
5. **Trình duyệt** đọc `ReadableStream`, giải mã ra text, đưa vào parser SSE.
   - Parser giữ phần đuôi chưa trọn dòng, nhận LF, CR hoặc CRLF (kể cả khi CR và LF rơi vào hai đoạn khác nhau), và gặp dòng trống thì kết thúc một event.
   - Mỗi event được Zod kiểm bằng schema dùng chung; sai tên hoặc sai dữ liệu thì dừng và báo câu trả lời bị gián đoạn.
6. **Reducer** đi `waiting → streaming → done`: chữ dài dần theo `token`. Marker `[n]` chỉ thành chip bấm được sau khi có `citations`, và chip mở tài liệu ở tab mới với các field được trích.

Đường đi của nút Dừng:
- Bấm Dừng gọi `AbortController.abort()`. Từ đó `fetch` của trình duyệt bị huỷ, và client tự `reader.cancel()` (không trông cậy vào việc `fetch` tự làm hỏng body).
- Kết nối tới BFF đóng, nên `req.signal` của BFF abort và fetch lên API bị huỷ.
- Socket của API đóng, và API huỷ lời gọi model đang chờ.
- UI chuyển sang `cancelled`; event nào tới muộn sau đó đều bị bỏ.

**Lưu ý**

- `EventSource` có gửi cookie khi gọi cùng origin. Lý do không dùng là GET và URL, không phải cookie.
- Đừng để BFF tự quyết quyền: như vậy là hai nơi cùng giữ một luật. BFF là lớp tiện lợi, API mới là lớp quyết định.
- Bước embed câu hỏi trên API vẫn chạy cho xong khi bị huỷ; chỉ lời gọi model là bị huỷ.
- Hỏi câu mới khi câu cũ đang chạy thì câu cũ bị abort, và cả event lẫn lỗi của nó không được lọt sang state của câu mới.

## Câu 3: SSE khác WebSocket thế nào, vì sao chọn SSE, chỗ có thể hỏng

**Câu hỏi**

SSE khác WebSocket thế nào, và vì sao ở đây chọn SSE? Nêu ít nhất một chỗ cách làm hiện tại có thể hỏng khi lên production, và người dùng sẽ thấy hiện tượng gì.

**Trả lời**

| | SSE | WebSocket |
|---|---|---|
| Chiều dữ liệu | Server → client | Hai chiều |
| Giao thức | HTTP thường | Nâng cấp kết nối (`Upgrade`), sau đó là giao thức riêng |
| Đi qua cookie, BFF, proxy | Như mọi request | Cần cấu hình riêng |
| Tự kết nối lại | `EventSource` có sẵn | Phải tự viết |
| Chỉ gửi được text | Đúng | Gửi được cả nhị phân |

Chọn SSE vì hỏi đáp là một câu hỏi, một luồng trả lời rồi đóng; không cần kênh hai chiều sống lâu. WebSocket sẽ cần thêm một cơ chế xác thực cho socket: ADR 0006 ghi rằng realtime cần token ngắn hạn lấy từ BFF. Ngoài ra còn cần proxy cho đường socket và tự xử lý vòng đời kết nối.

Chỗ có thể hỏng trên production:
- **Proxy nén hoặc buffer `text/event-stream`** (Caddy có `encode zstd gzip`, chưa kiểm). Event bị gom tới cuối. Nhờ "kiểm xong mới phát", nội dung vẫn đúng, chỉ là chữ hiện ra một cục.
- **Proxy hoặc load balancer có idle timeout ngắn hơn quãng im lặng trước byte đầu tiên** (thường là 60 giây). Nó cắt kết nối trong khi API vẫn đang xử lý. Web thấy lỗi mạng, hoặc thấy "stream đứt trước `done`" và báo câu trả lời bị gián đoạn.
- **Chạm timeout 90 giây của chính BFF.** BFF trả `504 UPSTREAM_UNAVAILABLE` và người dùng thấy câu báo lỗi đã dịch.

**Lưu ý**

- WebSocket không "trái" cookie httpOnly: lúc bắt tay kết nối nó vẫn gửi cookie. Nhược điểm nằm ở cách triển khai (thêm cơ chế xác thực, thêm đường proxy), không phải ở cookie.
- Mốc 90 giây là timeout của BFF, không phải của proxy. Rủi ro thật là một proxy cắt sớm hơn mốc đó.
- Cách chữa idle timeout là comment `: ping` định kỳ. Muốn làm thì API phải mở SSE trước khi quyết xong câu trả lời, nên lỗi trước khi phát không còn là Problem Details nữa, tức là đổi hợp đồng của T5.4. Vì vậy task này chưa làm.
- Drill bỏ `no-transform` vẫn xanh vì bản build production của Next không nén `text/event-stream`. Nghĩa là header đó hiện chỉ có tác dụng với proxy phía trước, chưa ai chứng minh trên Caddy.
