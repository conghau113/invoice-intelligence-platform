# T1.7 — Gate notes: UI theo quyền so với kiểm soát ở backend, chọn tenant

## Câu 1 — Ẩn menu có phải bảo mật không

**Câu hỏi:** Ẩn mục "Thành viên" khỏi menu của viewer có phải là bảo mật không? Nếu chỉ giữ việc ẩn menu và bỏ kiểm quyền ở API thì chuyện gì xảy ra?

**Trả lời:** Không. Ẩn menu chỉ là tiện dụng: bỏ lối cụt, tránh nhầm lẫn. Mọi thứ chạy trên trình duyệt đều do người dùng kiểm soát (DevTools, curl, sửa HTML), nên chỉ kiểm tra ở server mới là ranh giới thật. Nếu bỏ kiểm quyền ở API thì ai có token hợp lệ (kể cả viewer) gọi thẳng endpoint quản trị được và làm việc vượt vai trò trong cùng tenant. RLS không cứu được chuyện này: RLS trả lời "dữ liệu của tenant nào", còn RBAC trả lời "được làm gì trong tenant". Ở đây menu lấy danh sách quyền từ `/auth/me` của chính API, và `PermissionsGuard` trả 403 cho mọi lời gọi thiếu quyền.

**Lưu ý:**
- API là deny-by-default: route quên khai báo quyền cũng bị 403 `FORBIDDEN_UNDECLARED`.
- Web không chép ma trận quyền; chép sẽ có hai nguồn sự thật dễ lệch.
- Menu trỏ tới trang chưa có (M2+) hiện 404, đó không phải bằng chứng về quyền.

## Câu 2 — Chọn tenant từ đầu đến cuối

**Câu hỏi:** Khi `consultant@demo.example` chọn "globex" trong dropdown, ai làm gì cho tới khi trang hiện dữ liệu globex, và vì sao việc chọn này không cho vào tenant không thuộc về họ?

**Trả lời:** (1) Trình duyệt gửi form POST same-origin tới `/api/tenant` với `tenant=globex`. (2) Server web kiểm Origin (chống CSRF), đọc session JWT httpOnly, chỉ nhận alias nằm trong `token.tenants`, ghi cookie httpOnly `tenant=globex` và chuyển hướng 303 về trang cũ. Keycloak không tham gia, không đăng nhập lại. (3) Khi render, server web lấy tenant từ cookie (không hợp lệ thì rơi về tenant đầu), gọi API kèm `Authorization: Bearer` và `X-Tenant: globex`; trình duyệt không thấy token. (4) API xác minh chữ ký JWT, lấy tập tenant từ claim `organization`, chỉ chấp nhận `X-Tenant` nếu nằm trong tập đó, tra alias thành `tenantId` trong DB, rồi mở transaction đặt `app.tenant_id` để RLS chỉ trả dữ liệu globex. Giả cookie hay giả header không cấp thêm quyền, vì tập tenant hợp lệ do Keycloak ký, client không tự khai được; alias lạ bị 403 `TENANT_NOT_MEMBER`.

**Lưu ý:**
- Hai lớp không ngang hàng: lớp web chỉ để tiện, API mới là ranh giới bảo mật duy nhất.
- Header chỉ là bộ chọn, không bao giờ là quyền. Header lặp thành chuỗi "a, b" nên không khớp alias nào và bị 403.
- Alias có trong claim nhưng không có trong DB cũng bị 403 "Unknown tenant".
- Không có header mà token có nhiều tenant: 403 `TENANT_REQUIRED`.

## Câu 3 — Đánh đổi: một token nhiều tenant so với đăng nhập lại

**Câu hỏi:** So với "đăng nhập lại mỗi lần đổi tenant", hướng "một token chứa mọi tenant, chọn bằng header" có ưu nhược gì và hỏng ở đâu?

**Trả lời:** Ưu: đổi tenant tức thì, giữ trang và trạng thái, đúng thiết kế API.md (API nhận lựa chọn rồi kiểm membership), e2e dễ viết. Nhược: token mang danh sách mọi tenant của user; vai trò là realm-wide nên cùng quyền ở mọi tenant; membership bị cũ trong thời hạn token. Hỏng ở đâu: (a) user vừa bị gỡ khỏi org trong Keycloak nhưng token cũ còn liệt kê org đó nên vẫn vào được cho tới khi token hết hạn hoặc được làm mới; (b) admin ở acme, chỉ nên là viewer ở globex, nhưng đổi sang globex vẫn mang quyền admin (RLS đúng tenant, RBAC sai mức); (c) `session.tenants` ở web chỉ đọc lúc đăng nhập nên dropdown có thể cũ hơn token đã làm mới. Khi cần thu hồi tức thì hoặc vai trò theo từng tenant thì chuyển membership và vai trò sang DB, hoặc rút ngắn thời hạn token và ép làm mới sớm.

**Lưu ý:**
- Vai trò theo tenant chưa có: ghi ở "Phát sinh", cần ADR trước khi có dữ liệu thật.
- Rút ngắn thời hạn access token giảm cửa sổ (a) mà không đổi kiến trúc.
- Sau (a), API trả 403 và giao diện hiện bảng lỗi kèm dropdown để chọn tenant khác.
