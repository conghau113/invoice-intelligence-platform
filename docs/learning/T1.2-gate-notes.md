# T1.2 — Ghi chú cổng hiểu: xác thực JWT qua JWKS

## Câu 1 — JWKS là gì, vì sao API không gọi Keycloak mỗi request?

**Câu hỏi:** JWKS là gì và giải quyết vấn đề gì cho API? Nếu không có JWKS mà vẫn muốn tin token Keycloak thì phải làm gì, thiếu hoặc bất tiện gì?

**Trả lời:** JWKS (JSON Web Key Set) là tài liệu JSON Keycloak công bố tại `/realms/invoice/protocol/openid-connect/certs`, chứa các public key. Keycloak ký access token bằng private key; header JWT có `kid` để chọn đúng public key trong JWKS. API tải JWKS một lần, cache lại, rồi tự verify chữ ký cùng `iss`, `aud`, `exp`, `nbf` mà không hỏi Keycloak mỗi request. Khi Keycloak xoay khóa, API gặp `kid` lạ thì tải lại JWKS, không cần deploy lại. Các phương án thay thế: introspection mỗi request (chậm, Keycloak chết thì API chết theo); hard-code public key (không xoay khóa tự động); chỉ decode không verify (ai cũng giả được); HMAC dùng chung secret (mọi bên giữ secret đều ký giả được).

**Lưu ý:**
- JWKS chỉ chứa public key. Private key không bao giờ rời Keycloak.
- Chữ ký đúng chưa đủ: phải kiểm thêm `iss` và `aud` (token cấp cho dịch vụ khác vẫn có chữ ký hợp lệ) và ghim `algorithms: ['RS256']` để chặn `alg=none` và tấn công đổi RS256 sang HS256 dùng public key làm secret.
- Verify offline đánh đổi khả năng thu hồi tức thì (xem câu 3).

## Câu 2 — Luồng một request đến lúc biết tenant

**Câu hỏi:** Từ header `Authorization: Bearer …` đến lúc handler biết tenant, ai làm gì ở mỗi bước? Tenant lấy từ đâu? Khi nào 401, khi nào 403?

**Trả lời:** Guard toàn cục (deny-by-default) chạy trước mọi route, trừ route `@Public()`. Guard tách Bearer token; thiếu hoặc sai định dạng thì 401. Verifier (`jose`) kiểm chữ ký RS256, `iss`, `aud`, `exp`, `nbf`; mọi lỗi đều thành 401 mà không nêu lý do. Bước ánh xạ claim lấy `sub` làm userId, lấy tenant từ claim `organization` (đúng một alias, rồi tra ra UUID tenant) và lọc role đã biết từ `realm_access.roles`; kết quả gắn vào `req.user`. Handler đọc `@CurrentUser()` hoặc `@CurrentTenant()`. Tenant không bao giờ lấy từ header hay body vì client tự đặt được; claim trong JWT đã ký thì client không sửa được. 401 nghĩa là không chứng minh được danh tính. 403 nghĩa là danh tính hợp lệ nhưng không gán được đúng một tenant (không có, nhiều, alias lạ).

**Lưu ý:**
- Claim `organization` chỉ xuất hiện khi client xin đúng scope. User nhiều tenant phải xin `organization:<alias>` lúc đăng nhập (T1.5, T1.7); xin `organization:*` sẽ nhận token nhiều tenant và bị API từ chối bằng 403.
- Từ T1.4, 403 còn có nghĩa "thiếu permission". Hai nguyên nhân dùng chung một mã, nên message và test phải phân biệt.
- Test dùng token tự ký nên không bắt được lỗi cấu hình Keycloak. Đã từng lệch: token thật thiếu `sub` vì client thiếu scope `basic`. Luôn kiểm thêm một lần với Keycloak thật.

## Câu 3 — Xoay khóa và đánh đổi của verify offline

**Câu hỏi:** Khi Keycloak xoay khóa, API xử lý từng bước thế nào và tình huống xấu nào có thể xảy ra? Cache JWKS mang lại gì và làm mất gì so với introspection? Flood token `kid` lạ gây hại gì và cơ chế nào giảm rủi ro?

**Trả lời:** Keycloak thêm khóa mới vào JWKS, rồi mới dùng nó để ký. Token mới mang `kid` mới; cache của API chưa có `kid` đó nên `jose` tải lại JWKS một lần (có `cooldownDuration`), lấy được key rồi verify. Token ký bằng key đã bị gỡ: sau khi refetch vẫn không thấy key thì 401. Cache và verify offline cho tốc độ cao, ít tải lên Keycloak, và Keycloak ngắt ngắn vẫn verify được token chưa hết hạn; đổi lại API không biết token đã bị thu hồi trước `exp` (introspection thì biết ngay nhưng chậm và phụ thuộc Keycloak). Gửi nhiều token `kid` lạ có thể khiến API dồn refetch vào Keycloak; `cooldownDuration` giới hạn tần suất refetch, trong lúc cooldown token `kid` lạ vẫn bị 401 mà Keycloak không bị hỏi. Rate limit ở tầng ngoài là lớp bổ sung về sau.

**Lưu ý:**
- Cửa sổ lỗi thực tế là cooldown: nếu vừa refetch xong mà key mới xuất hiện ngay sau, token mang `kid` mới bị 401 đến khi cooldown hết (30 giây trong code hiện tại). Cooldown chặn flood nhưng đổi lại 401 tạm thời.
- Key bị gỡ vẫn verify được từ cache cho đến khi refetch hoặc cache hết hạn (`cacheMaxAge` 10 phút). Key bị lộ thì cần rút ngắn cache hoặc khởi động lại API; chưa có cơ chế tức thì.
- Keycloak chết đúng lúc refetch: hiện API trả 401, client tưởng token sai. Về lý thuyết đúng hơn là 503 (lỗi tạm thời). Đã ghi vào "Phát sinh" của `TASKS.md`.
- Access token phải sống ngắn (vài phút) vì API không thu hồi sớm được; refresh token là việc của BFF ở web (T1.5).
