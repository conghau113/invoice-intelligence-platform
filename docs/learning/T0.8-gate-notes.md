# T0.8 — Ghi chú cổng hiểu (Script kiểm tra repo: automated governance)

## 1. Automated governance là gì và vai trò trong hệ thống

**Câu hỏi:** Automated governance là gì và giải quyết vấn đề gì trong dự án này? Nếu không có `check:i18n`, `check:adr`, `check:links` thì điều gì hỏng hoặc bị bỏ sót, và vì sao chỉ dựa vào người review là chưa đủ? Lỗi nào máy bắt tốt hơn người, lỗi nào thì không?

**Trả lời:** Là biến các quy ước của repo thành script chạy trong CI: mỗi PR máy tự kiểm những điều kiểm được bằng quy tắc rõ, đỏ thì chưa được coi là xong. Trong dự án, nó chặn lệch khóa hoặc tham số giữa `vi.json` và `en.json`, ADR không có trong bảng index, link docs gãy sau khi đổi tên file. Không có cổng thì thiếu bản dịch chỉ lộ ở runtime, ADR mới "mồ côi" không ai tra ra, docs "Đọc trước" trỏ 404. Người review kém ổn định ở lỗi rải rác và nhàm (hàng trăm key, chục ADR, trăm link), nhất là khi AI sửa nhiều file một lúc. Máy bắt tốt: lệch khóa/tham số, ADR thiếu trong bảng, link gãy, schema drift, secret theo pattern. Người bắt tốt: bản dịch sai nghĩa, ADR mâu thuẫn ADR cũ, docs giải thích sai, bug nghiệp vụ, thiếu test, UX. Máy giữ tính nhất quán, người giữ đúng sai về ý nghĩa.

**Lưu ý:**

- **Cổng không thể fail là cổng vô dụng** (WORKFLOW §5): mỗi cổng phải có một test âm, nếu không script hỏng luôn in `OK` sẽ tạo cảm giác an toàn giả.
- Cổng chỉ có tác dụng khi bị ép: chạy trong CI mới ngăn được việc quên, và chỉ chặn merge khi bật branch protection với required status checks (hiện CI mới báo, chưa chặn).
- Xanh không có nghĩa là đã kiểm. `check:i18n` hiện SKIP vì chưa có `messages/`; phải phân biệt "đã kiểm và đạt" với "chưa kiểm". Code-reviewer từng bắt đúng lỗi SKIP in cả `OK`.
- Máy chỉ bắt những gì đã được mã hóa thành luật. Cổng không thay review thiết kế hay bảo mật.

## 2. Luồng chạy từ push đến PR đỏ

**Câu hỏi:** PR thêm ADR `0019-foo.md` nhưng quên dòng trong README, đồng thời đổi tên một file docs còn link cũ. Từ push đến khi PR đỏ điều gì xảy ra? Mỗi script phát hiện lỗi bằng ý tưởng gì? Làm sao biết chắc cổng thật sự đỏ khi dữ liệu sai?

**Trả lời:** Push và mở PR phát sinh sự kiện `pull_request`; GitHub đọc `ci.yml` và khởi máy ảo Ubuntu cho job `repo-checks`: checkout, bật Node, rồi chạy tuần tự `check:i18n`, `check:adr`, `check:links`, `test:scripts`. `check:adr` lấy danh sách file `NNNN-*.md` (trừ template), lấy các link trong dòng bảng của README và so hai tập theo cả hai chiều: file có mà bảng thiếu, bảng có mà file không tồn tại. `check:links` duyệt `.md`, bỏ code fence và code inline, tìm `](đích)`, bỏ `http(s)`, resolve đường dẫn tương đối từ file chứa link rồi hỏi file đó có tồn tại không, và nếu có `#anchor` thì so với slug các heading của file đích. Lỗi thì `report` trả exit code 1, step đỏ, job đỏ, PR hiện check đỏ. Biết cổng thật sự đỏ nhờ test âm chạy script thật trên fixture sai (kiểm exit 1 và nội dung lỗi), thử phá trên repo thật rồi hoàn tác, và nguyên tắc chưa thấy đỏ đúng chỗ thì chưa tin lúc xanh.

**Lưu ý:**

- Trong một job, **step đỏ làm các step sau bị bỏ qua** (không phải "có thể"): tác giả chỉ thấy lỗi ADR, sửa xong mới thấy lỗi link ở vòng sau. Đây là đánh đổi của thiết kế một job nhiều step.
- Dấu đỏ trên PR không tự chặn merge; chỉ chặn khi có branch protection với required status checks.
- `test:scripts` kiểm *logic* của script trên fixture, không kiểm repo thật; repo thật do chính `check:*` kiểm.
- Cổng tự siết: `check:i18n` chuyển từ SKIP sang nghiêm ngay khi `apps/web/package.json` có `next-intl`, không cần nhớ sửa tay.

## 3. Đánh đổi: tự viết 3 script thay vì phương án khác

**Câu hỏi:** Vì sao tự viết script Node thay vì dùng thư viện kiểm link, chạy qua Turborepo, hoặc chỉ dựa vào review? Cách tự viết có thể sai ở đâu (ít nhất hai kiểu), biểu hiện ra sao? Khi nào cổng xanh trên CI mà thực ra không kiểm gì, và phát hiện bằng cách nào?

**Trả lời:** Thư viện (`markdown-link-check`, `remark-validate-links`) thêm dependency phải duyệt giấy phép trong `LEGAL.md`, một số gọi mạng làm CI chập chờn, và bạn phải giải thích được code. Turborepo bị loại vì `turbo.json` có `inputs: ["!**/*.md"]`: đổi markdown không đổi hash nên cache hit và xanh giả đúng lúc cần soi docs/ADR. Chỉ dựa vào review thì lỗi nhàm dễ sót và không lặp lại ổn định mỗi PR. Dùng `git ls-files` bị loại vì cần spawn theo PATH và bỏ sót file chưa add. Báo nhầm (đỏ oan): slug anchor lệch GitHub, hoặc URL có `)` bị cắt sớm, nên CI đỏ dù link mở được. Bỏ sót (xanh oan): không kiểm `http(s)`, reference-style, `<a href>`; ICU chỉ so tham số cấp ngoài nên bản en thiếu `name` trong nhánh plural vẫn qua. Xanh mà không kiểm gì: cổng SKIP bị coi như OK, script luôn `exit 0`, chạy qua Turbo bị cache, step bị filter nhưng check vẫn hiện xanh. Phát hiện bằng test âm, phá thử có chủ đích, và log phân biệt rõ `OK`, `FAIL`, `SKIP`.

**Lưu ý:**

- Giới hạn đã biết, ghi trong task note: ICU apostrophe `'{'` và tham số lồng nhánh không được so; link có ngoặc đơn trong đích (`foo_(bar).md`) bị cắt; không kiểm reference-style, `<a href>`, `http(s)`.
- Fixture JSON cố tình sai cú pháp phải nằm trong `.prettierignore`, nếu không Prettier tự sửa và test âm mất tác dụng.
- Tránh `os.tmpdir()` và `spawn` theo PATH vì SonarCloud gắn cờ; dùng fixture commit sẵn, `--root` và `process.execPath`.
- Code-reviewer tìm ra 10 điểm sau lần viết đầu (SKIP in `OK`, một file messages vẫn qua, slug bỏ nhầm `_`, link badge, fence 4 dấu...): bản nháp đầu của agent chưa đủ chặt, cần review độc lập.
