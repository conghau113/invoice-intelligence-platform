# T0.4 — Ghi chú cổng hiểu (apps/ai: FastAPI + uv + pytest)

## 1. Luồng chạy

**Câu hỏi:** Khi chạy `uv run uvicorn app.main:app --port 8000` rồi gửi `GET /health`, luồng từ đầu đến cuối là gì?

**Trả lời:** Uvicorn là server ASGI. Nó import module `app.main`, lấy thuộc tính `app`, rồi lắng nghe cổng. Khi import, `app/main.py` chạy từ trên xuống: import `app.config` (chỉ khai báo `Settings`, `get_settings`), import `app.routers.health` (decorator `@router.get("/health")` đăng ký route vào `router`), định nghĩa `create_app`, rồi dòng cuối `app = create_app()` chạy ngay: `get_settings()` dựng `Settings()` (pydantic đọc biến môi trường và file env, kiểm tra `ENV`, `PORT`, `LOG_LEVEL`), tạo `FastAPI`, `include_router(health.router)`. Mỗi request, Uvicorn gọi `await app(scope, receive, send)`; Starlette khớp route và gọi `health()`; FastAPI biến dict thành JSON.

**Lưu ý:**

- `include_router` mới làm app biết route; decorator chỉ đăng ký vào `router`.
- `--port` là cờ của Uvicorn, không đọc `Settings.port`. `port` và `log_level` hiện chưa có tác dụng.
- File env được tìm theo thư mục làm việc (cwd), không theo vị trí `config.py`. Chạy `uv run` từ gốc repo sẽ lỗi `Failed to spawn: uvicorn` vì không có `pyproject.toml`; phải đứng ở `apps/ai` hoặc dùng `uv run --directory apps/ai`.
- `get_settings()` có `lru_cache`: mỗi tiến trình chỉ tạo Settings một lần. Test phải `cache_clear()`.
- Ban đầu `Settings` chưa được nối vào `create_app()` (agent bỏ sót); reviewer phát hiện, đã sửa.

## 2. Vì sao chọn cách này

**Câu hỏi:** Vì sao Dockerfile chia 2 stage và chạy user không phải root? Vì sao uv thay pip? Vì sao `create_app()` là factory?

**Trả lời:** Stage `builder` cài dependency production (`uv sync --frozen --no-dev`); stage `runtime` chỉ copy `.venv` và `app`, không có `uv`, `pytest`, `ruff`, `tests`. Image nhỏ, ít công cụ để bị lợi dụng, bất biến (đổi dependency thì build lại, khớp `uv.lock`). Copy `pyproject.toml` và `uv.lock` trước nên sửa code không làm cài lại dependency. Chạy `appuser` (uid 10001) để nếu bị chiếm thì không có quyền root trong container. uv khoá cả cây phụ thuộc, tách nhóm dev, nhanh, một công cụ cho cả chạy lẫn test; đánh đổi là phải cài uv. Phương án khác: pip + pip-tools. Factory cho phép test tạo app riêng theo config tại lúc gọi, nên test được trường hợp config sai mà không cần `importlib.reload`.

**Lưu ý:**

- "Không cài thêm gói trong container" là mục tiêu, không phải hại. Cái hại thật là khó debug vì thiếu công cụ.
- `.venv` từ `builder` liên kết tới Python của `builder`; chạy được vì cả hai là Python 3.12 và cùng đường dẫn `/app`. Đổi phiên bản một bên sẽ vỡ.
- uvicorn có cờ `--factory`; repo giữ `app = create_app()` cho đơn giản.

## 3. Hỏng ở đâu

**Câu hỏi:** Nếu `ENV=staging` thì lỗi lộ ở đâu, lúc nào, test nào bắt? `/health` có phát hiện dependency chết không? Test nào chưa chứng minh đủ?

**Trả lời:** Lỗi không lộ lúc build (`uv sync` không import app) và không đợi request. Nó nổ lúc Uvicorn import `app.main`, ở `app = create_app()`, trước khi listen. `test_invalid_value_fails_fast` (tầng `Settings`) và `test_create_app_fails_fast_on_invalid_config` (tầng `create_app`) bắt được. `/health` chỉ là liveness, nên LLM provider chết vẫn trả 200; readiness là câu hỏi khác. Gộp hai thứ vào một endpoint khiến orchestrator restart tiến trình khỏe mà không làm provider sống lại. `test_health_returns_ok` tự gọi `create_app()` nên không khoá biến `app` ở cuối `main.py`, là thứ Uvicorn thật sự lấy.

**Lưu ý:**

- Đổi dòng cuối thành `app = FastAPI()` trống thì pytest vẫn xanh, server thật trả 404. Nên có test dùng `from app.main import app`.
- Vì `app = create_app()` chạy lúc import, `from app.main import ...` ở đầu file test đã đọc biến môi trường; `ENV` sai trong CI sẽ làm pytest lỗi ngay lúc thu thập test.
- Thường tách `/health` (liveness) và `/ready` (readiness) khi đã có provider thật.

## 4. Cổng hiểu: vì sao tách AI ra dịch vụ Python?

**Câu hỏi:** Vì sao tách AI ra dịch vụ Python thay vì gọi LLM thẳng từ NestJS? Đánh đổi là gì?

**Trả lời:** Hệ sinh thái Python mạnh cho PDF/ảnh, embedding và SDK LLM (ADR 0002). `apps/ai` stateless: không có database, không thấy danh tính, chỉ nhận file hoặc text theo tenant. Việc nặng CPU (rasterize PDF, xử lý ảnh) không chặn event loop của API. Cuộc gọi LLM dài cần timeout, retry và cách ly lỗi. Hai phần mở rộng độc lập, và phạm vi ảnh hưởng nhỏ: tiến trình xử lý tài liệu không chạm DB. Output model là dữ liệu không tin cậy: validate bằng schema, chạy business rule, không thực thi, không để viết SQL. Đánh đổi: thêm một chặng mạng, một contract phải khớp hai ngôn ngữ (Zod → JSON Schema, cần CI kiểm tra drift, ADR 0004), thêm một runtime để build, deploy, theo dõi.

**Lưu ý:**

- Đừng nói "chờ LLM làm kẹt Nest": Node xử lý I/O bất đồng bộ, chờ response không chặn event loop. Vấn đề thật là việc nặng CPU, timeout/retry, mở rộng độc lập và giới hạn phạm vi ảnh hưởng.
- Schema lệch thì trích xuất fail dù model trả lời đúng ý.
