# T2.5 — Gate notes: BFF proxy, hàng đợi upload phía client, đánh đổi

## Câu 1 — Proxy upload trong Next là gì và vai trò

**Câu hỏi:** Upload của trình duyệt đi qua một route proxy trong Next rồi mới tới API. Proxy này là gì, giải quyết vấn đề gì, và nếu bỏ nó thì cái gì hỏng hoặc thiếu?

**Trả lời:** Đây là phần BFF (Backend For Frontend) của ADR 0006. Token đăng nhập nằm trong cookie httpOnly nên JavaScript của trang không đọc được, tức trình duyệt không có token để gọi API. Trình duyệt gửi multipart cùng origin tới `POST /api/documents/upload`; route này đọc session phía server, gắn `Authorization: Bearer` và `X-Tenant`, chuyển `Idempotency-Key`, truyền body sang API dạng stream, rồi trả nguyên status và body. Nếu bỏ nó, chỉ còn hai đường: đưa token ra trình duyệt (XSS đánh cắp được, trái ADR 0006) hoặc không upload được, vì API chỉ nhận Bearer. Có thêm CORS và việc để lộ API trực tiếp.

**Lưu ý:**
- Cookie `tenant` chỉ là lựa chọn của người dùng. API vẫn đối chiếu `X-Tenant` với claim trong token đã ký, nên proxy không phải chỗ quyết định bảo mật.
- Xác thực bằng cookie thì phải chống CSRF: route tự từ chối request thiếu hoặc sai `Origin` (`SameSite=Lax` chưa đủ để dựa hoàn toàn vào). Xác thực bằng header Bearer do JS gắn thì không có rủi ro này.
- `proxy.ts` (ex-middleware) cũng chạy trên `/api/*`: nó làm refresh token và, sau code-review, trả 401 JSON cho `/api/*` khi chưa đăng nhập. Nếu để nó redirect, XHR đọc trang login như "200".
- Proxy không đọc hay log nội dung file; chỉ chuyển tiếp một danh sách header cố định, không chuyển cookie.

## Câu 2 — Một lần thả 5 file, từ đầu đến cuối phía trình duyệt

**Câu hỏi:** Người dùng thả 5 file. Kể chuyện gì xảy ra: bao nhiêu file gửi cùng lúc và cái gì quyết định; một file lỗi hoặc bị huỷ thì file còn lại và slot ra sao; bấm "Thử lại" vì sao không sinh document trùng?

**Trả lời:** Dropzone đưa 5 `File` vào `UploadQueue.add`. Mỗi file được kiểm client (sai loại, rỗng, quá 10 MiB → `error` ngay, không gửi); file hợp lệ thành `pending` và được sinh một `Idempotency-Key`. `pump()` khởi động tối đa 3 file (`MAX_CONCURRENT_UPLOADS`), mỗi file là một XHR có sự kiện tiến độ; 2 file còn lại chờ. Mỗi khi một file kết thúc, `pump()` lấy file chờ tiếp theo vào slot trống. Một file lỗi hoặc bị huỷ chỉ đổi trạng thái của chính nó; slot được giải phóng ngay (huỷ thì `abort()` XHR), và kết quả muộn của lần đã huỷ bị bỏ nhờ so số lần thử (`attempt`). "Thử lại" giữ nguyên key đã sinh lúc `add`, nên gửi lại cùng key và cùng bytes thì API trả lại kết quả cũ thay vì tạo document mới.

**Lưu ý:**
- Server có hai lớp chống trùng độc lập: `Idempotency-Key` lưu 24 giờ (cứu trường hợp server đã nhận nhưng response bị mất, trả 200 + `Idempotent-Replayed`) và ràng buộc duy nhất (tenant, content hash) (cùng bytes khác key hoặc khác tên vẫn ra document cũ, UI hiện "Đã có sẵn").
- Huỷ XHR không đảm bảo server chưa tạo document: file có thể đã ghi xong trước khi thấy kết nối đứt. Thử lại sau khi huỷ vẫn an toàn nhờ hai lớp trên.
- Không phải lỗi nào cũng thử lại được: loại file sai, quá lớn, thiếu quyền, `idempotency` (cùng key + cùng file sẽ bị từ chối lại) và `sessionExpired` (phải đăng nhập) không có nút Thử lại.
- Rời trang thì `cancelAll` huỷ file đang chạy và không bắt đầu file đang chờ; nếu không, upload chạy nền mà không có UI nào hiện kết quả.
- Thanh tiến độ đạt 100% khi trình duyệt gửi xong tới proxy Next, API có thể còn đang kiểm, băm và xếp hàng.

## Câu 3 — Đánh đổi: giới hạn song song, upload qua API, lỗi cắt im lặng

**Câu hỏi:** (a) Vì sao giới hạn upload song song ở 3, không phải 1 hay 20? (b) Upload qua API (proxy) khác presigned URL thế nào, đánh đổi là gì, khi nào nên đổi? (c) Trong task này có thứ gì im lặng làm hỏng file mà không báo lỗi, nằm ở đâu, phát hiện bằng cách nào?

**Trả lời:** (a) 1 thì quá chậm khi thả nhiều file. 20 thì các upload tranh băng thông và pool kết nối, dễ timeout hoặc 503 ở phía server, và RAM của web tăng vì mỗi upload đang chạy giữ tới ~11MB. 3 đủ song song để thấy nhanh mà không đè một VM demo. (b) Qua API thì API kiểm xác thực, magic bytes, kích thước và idempotency trước khi file vào kho, khớp BFF (token không ra trình duyệt) và `LocalFs` đơn giản; đổi lại API/web gánh băng thông và CPU, khó scale ngang. Presigned URL cho trình duyệt đẩy thẳng lên kho nên API nhẹ, nhưng phức tạp hơn (S3 hoặc SeaweedFS, CORS, policy), phải kiểm loại file trước hoặc sau theo cách khác, và dễ lệch ADR 0006/0017 nếu lộ credential. Nên đổi khi có nhiều instance cần storage dùng chung, file lớn và nhiều, hoặc làm O1 (SeaweedFS). (c) Next đệm body cho `proxy.ts` chạy trên `/api/*`: mặc định 10MB, phần vượt bị cắt mà không báo lỗi, nên file sát 10 MiB tới API bị cụt. Sửa ở `next.config.ts` bằng `proxyClientMaxBodySize: '11mb'`; test e2e gửi file đúng 10 MiB đỏ khi hạ xuống 1mb.

**Lưu ý:**
- Chi phí của việc đệm: mỗi upload đang chạy giữ tới 11MB trong RAM của web, và 3 song song là ~33MB; tăng số song song thì tăng RAM theo.
- Route có 413 sớm dựa vào `Content-Length` do client khai; request không có header này chỉ bị chặn bởi `proxyClientMaxBodySize` (cắt im lặng) và giới hạn multer ở API. API là nơi quyết định cuối.
- Hằng số 10 MiB và danh sách loại file nằm ở hai nơi (API và `validate.ts`), chỉ khớp bằng comment. Kiểm client chỉ để tiện, vì tên file và MIME do người dùng khai.
- Loại lỗi này (hỏng im lặng) chỉ bắt được bằng test chạy đường thật với dữ liệu sát giới hạn; unit test với mock không thấy.
- CI `e2e` build production chưa chạy thật; test 10 MiB phụ thuộc `next.config.ts` được đọc lúc `next start`.
