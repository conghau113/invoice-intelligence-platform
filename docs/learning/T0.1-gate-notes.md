# T0.1 — Ghi chú cổng hiểu

Liên quan: `package.json`, `pnpm-workspace.yaml`, `turbo.json`, `tsconfig.base.json`.

---

## Câu 1 — Luồng chạy của `pnpm turbo run lint`

**Câu hỏi:** Turbo biết có package nào bằng cách nào? Vì sao 0 package mà không lỗi? `pnpm-workspace.yaml` và `turbo.json` mỗi file làm gì?

**Trả lời:**
1. Turbo không tự quét thư mục. Nó đọc `pnpm-workspace.yaml` (glob `apps/*`, `packages/*`).
2. Thư mục khớp glob mà có `package.json` là một package.
3. Chưa có `apps/` hay `packages/` nên danh sách rỗng. Tập rỗng là hợp lệ, turbo chỉ cảnh báo `No tasks were executed`.
4. `package.json` gốc không được tính là package để chạy task, nếu không `lint` gốc gọi `turbo run lint` sẽ lặp vô hạn.
5. `pnpm-workspace.yaml` trả lời "ai là package"; `turbo.json` trả lời "chạy thế nào" (`dependsOn`, `inputs`, `outputs`, cache). Turbo chạy script tên `lint` trong `package.json` của từng package; package không có script đó thì bị bỏ qua.

**Lưu ý:**
- Thêm `apps/web` mà không sửa `pnpm-workspace.yaml` thì vẫn chạy, vì `apps/*` đã khớp sẵn. Luôn kiểm tra glob trước khi kết luận.
- Turbo không thấy package khi: nằm ngoài glob (ví dụ `tools/invoice-gen`, `eval/`), thiếu `package.json`, hoặc lồng sâu hơn một cấp (`*` chỉ khớp một cấp).
- Bài tập áp dụng: `apps/web` và `tools/invoice-gen` đều có script `lint`, workspace chỉ có `apps/*` và `packages/*` → chỉ `apps/web` chạy (1 package), `tools/invoice-gen` bị bỏ sót vì nằm ngoài glob. Trả lời cho tình huống giả định, không phải trạng thái hiện tại của repo.

## Câu 2 — Vì sao `tsconfig.base.json` chỉ giữ cờ strict

**Câu hỏi:** Vì sao bỏ `module`, `moduleResolution`, `lib`, `target` khỏi file nền? Để `NodeNext` trong nền thì đánh đổi gì?

**Trả lời:**
- Cờ chặt chẽ (`strict`, `noUncheckedIndexedAccess`, `noImplicitOverride`, `noFallthroughCasesInSwitch`, `forceConsistentCasingInFileNames`, `isolatedModules`) chỉ quyết định mức nghiêm khắc kiểm tra kiểu, mọi app muốn giống nhau, nên đặt ở nền.
- Cờ môi trường chạy (`module`, `moduleResolution`, `lib`, `target`) nói code chạy ở đâu và đóng gói thế nào, mỗi app khác nhau:

| | Next.js (T0.2) | NestJS (T0.3) |
|---|---|---|
| `module` | `esnext` | `commonjs` |
| `moduleResolution` | `bundler` | `node` |
| `lib` | thêm `DOM` | không cần DOM |
| Khác | `jsx: preserve`, `noEmit` | `experimentalDecorators`, `emitDecoratorMetadata` |

- Nếu để `NodeNext` trong nền: Next.js bị buộc import tương đối có đuôi `.js` và `next build` có thể tự sửa tsconfig; NestJS phải chọn CJS hay ESM sớm; quên ghi đè ở một app thì lỗi chỉ lộ lúc build.
- Cách tách có giá là mỗi app tự viết thêm vài dòng, nhưng không có giá trị mặc định sai ngầm.

**Lưu ý:**
- Agent đã sai: bản đầu đặt `NodeNext` trong nền, reviewer chỉ ra là không khớp các app sắp scaffold.
- Package kế thừa nền (ví dụ `packages/contracts`) vẫn cần tsconfig riêng: `extends`, `module`/`moduleResolution`, `target`, `lib` (Zod không cần DOM), `include`, và `outDir`/`declaration` nếu build ra `dist/`. Nền không có `include` nên `tsc -p tsconfig.base.json` báo `TS18003`.

## Câu 3 — `outputs` sai thì hỏng ở đâu

**Câu hỏi:** `outputs` của `build` ghi `build/**` nhưng app ra `dist/`. Lỗi lộ ở đâu, khi nào, test nào bắt được?

**Trả lời:**
1. Lần đầu build, `dist/` được tạo nhưng turbo không lưu vào cache (không khớp `outputs`).
2. Máy đó vẫn chạy bình thường vì `dist/` còn trên đĩa, lỗi bị che.
3. Lỗi lộ khi `dist/` biến mất mà khóa cache còn (xóa `dist/` rồi build lại, hoặc CI sạch có khôi phục cache). Turbo báo `cache hit, replaying logs` và coi là thành công, nhưng `dist/` không được tạo lại.
4. Task phụ thuộc `^build` sau đó mới lỗi, hoặc bản deploy thiếu file.
5. Test bắt được phải kiểm tra theo hành vi: build, xóa `dist/`, build lại, xác nhận có `cache hit` và `dist/` được khôi phục. Unit test thường và test grep chuỗi trong source không bắt được.

**Lưu ý:**
- Lỗi nằm ở task sau chứ không ở task cấu hình sai, nên khó dò.
- Chưa thử được ở T0.1 vì chưa có package; làm kiểm tra này ở T0.2.
- Biến thể cùng loại: `inputs` bị thu hẹp thành danh sách cố định (ví dụ chỉ `src/**`) thì đổi `tsconfig.json` không đổi hash → `cache hit`, typecheck bị bỏ qua, CI xanh giả. Kiểm tra theo hành vi: đổi một cờ trong `tsconfig.json`, chạy lại `typecheck`, phải thấy cache **miss**; so sánh bằng `--force`.
- Cấu hình hiện tại dùng `["$TURBO_DEFAULT$", "!**/*.md"]` (mặc định gồm cả `tsconfig.json`, loại trừ bớt) thay vì whitelist, nên không dính lỗi này.

## Câu 4 — Câu hỏi "Cổng hiểu" của task

### 4a. Turborepo cache dựa vào gì để biết task không cần chạy lại?

**Trả lời:** Turbo băm các yếu tố sau thành một khóa: `inputs`, hash của task phụ thuộc qua `dependsOn`, cấu hình task (`turbo.json`, `package.json`), biến môi trường khai báo (`env`/`globalEnv`), và phiên bản dependency bên ngoài (từ `pnpm-lock.yaml`). Khóa trùng và có cache thì bỏ qua việc chạy, phát lại log, khôi phục `outputs`.

**Lưu ý:** Phần lockfile dễ quên: đổi version một thư viện là cache bị vô hiệu dù không sửa file nguồn nào.

### 4b. pnpm khác npm workspaces ở điểm nào?

**Trả lời:**
- npm hoist dependency lên `node_modules` gốc. Package có thể `import` thứ chưa khai báo vì nó nằm ở cấp trên: đó là phantom dependency, chạy ở máy này nhưng hỏng khi hoisting đổi hoặc khi đóng gói riêng.
- pnpm đặt package thật trong `node_modules/.pnpm` (hard link từ store dùng chung). `node_modules` của mỗi package chỉ chứa symlink tới đúng dependency nó khai báo, nên import thứ không khai báo sẽ báo lỗi ngay.

**Lưu ý:**
- pnpm chặn chứ không chỉ "hạn chế". Store dùng chung còn tiết kiệm đĩa.
- Kết quả cụ thể, không nói chung chung: `apps/api` import `zod` mà không khai báo → với pnpm, lỗi `Cannot find module 'zod'` ngay lúc chạy hoặc typecheck; với npm hoisting nó có thể vẫn chạy.
- Ngoại lệ có thật: nếu `zod` được khai báo ở `package.json` gốc, Node tìm ngược lên thư mục cha và vẫn thấy nó. Vì vậy dependency phải khai báo trong chính package dùng nó.
