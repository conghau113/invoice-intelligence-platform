# T2.3 — Gate notes: Idempotency, at-least-once và đánh đổi khi upload

## Câu 1 — Idempotency là gì và vai trò trong upload

**Câu hỏi:** Idempotency là gì, giải quyết vấn đề gì khi người dùng upload hóa đơn? Nếu thiếu cả `Idempotency-Key` lẫn unique theo hash nội dung thì chuyện gì xảy ra khi mạng chập chờn và client gửi lại?

**Trả lời:** Idempotent = thực hiện cùng một thao tác nhiều lần cho cùng kết quả, không thêm tác dụng phụ. Client không phân biệt được "server chưa làm" với "server làm rồi nhưng response bị mất", nên buộc phải retry (hệ thống là at-least-once). Hai lớp bảo vệ khác nhau: `Idempotency-Key` chống trùng theo *request* (trả đúng response cũ, kể cả mã 201; cùng key khác file → 422); `UNIQUE (tenant_id, content_hash)` chống trùng theo *nội dung* (mọi key, mọi người dùng). Thiếu cả hai: mỗi retry tạo document mới, sau này enqueue thêm job, gọi AI nhiều lần, tốn quota, danh sách và audit bị lặp.

**Lưu ý:**
- Cần cả hai: key mới + file cũ thì unique bắt; key cũ + response bị mất thì key bắt. Không cái nào thay được cái kia.
- Key chỉ gắn với tenant, không gắn với user hay route: user thứ hai cùng tenant dùng lại key với cùng file nhận document của user đầu (đã chấp nhận).
- "Replay trong 24h": quá hạn thì key bị thay bằng request mới; không có job dọn hàng loạt (M7/M8).
- Kiểm "1 job" ở T2.3 chỉ là `created` + một dòng audit; job thật thuộc T2.4.

## Câu 2 — Hai request giống hệt đến cùng lúc

**Câu hỏi:** Kể từ đầu đến cuối chuyện gì xảy ra khi hai request cùng file, cùng key đến gần như cùng lúc. Vì sao chỉ có một document và một `created=true`? File của request thứ hai thì sao?

**Trả lời:** Guard kiểm key → multer ghi mỗi request một file riêng (cùng sha256) → mỗi bên một transaction ngắn. Cả hai đọc "chưa có key". Bên nào insert `documents` trước chiếm entry trong unique index; bên kia bị chặn ở chính lệnh insert (`ON CONFLICT DO NOTHING`) đến khi bên đầu commit, rồi không ghi gì và đọc lại document đã commit (READ COMMITTED: câu lệnh sau thấy dữ liệu đã commit). Insert key cũng `ON CONFLICT DO NOTHING`: bên thua replay theo dòng của bên thắng. Audit `document.created` chỉ ghi khi `created=true`, cùng transaction với document. Cuối cùng file của bên thua bị `discard` xoá.

**Lưu ý:**
- Không phải "ai commit trước thắng" mà là "ai insert trước chiếm chỗ, bên kia chờ". Nếu bên đầu rollback (ví dụ 422) thì bên chờ được đi tiếp và tự insert.
- "SELECT rồi INSERT" không có `ON CONFLICT` là sai: hai bên cùng thấy "chưa có", một bên lỗi unique.
- Mọi transaction lấy khoá theo cùng thứ tự (document rồi key) nên không có deadlock vòng.
- Test song song 5 request (cùng key, và khác key) là bằng chứng; drill bỏ `ON CONFLICT` → đỏ.

## Câu 3 — Bỏ transaction cả request và hai cửa sổ lỗi file

**Câu hỏi:** Vì sao route upload bỏ transaction cả request, và đánh đổi gì? Chỉ ra cửa sổ lỗi làm file mồ côi và cửa sổ làm document mất file; vì sao không xoá file ở mọi lỗi?

**Trả lời:** Giữ transaction suốt lúc client stream chiếm một connection của pool (max 10, chờ tối đa 5s) trong khi DB không làm gì: vài upload chậm là cạn pool và kéo theo cả request khác. Bỏ nó thì pool chỉ bị giữ vài ms lúc ghi DB, nhưng file và dòng DB không còn atomic và handler phải tự gọi `TenantDbService.run` (gọi `current()` sẽ ném lỗi, đóng an toàn). File mồ côi: file đã ghi nhưng không có document trỏ tới (trùng, 422, crash trước commit). Trùng/422 xoá ngay; crash để job dọn (M7/M8). Document mất file: lỗi không chắc đã rollback (mất kết nối lúc ack COMMIT) mà xoá file thì document đã commit mất file. Vì vậy chỉ xoá khi chắc chắn không còn ai trỏ tới (`created=false` hoặc 422).

**Lưu ý:**
- File mồ côi vô hại hơn document không có file; thà dư file.
- Agent ban đầu xoá file ở mọi lỗi; code-reviewer bắt và có test `commit-then-fail` + drill.
- `@SkipTenantTransaction` vẫn xác thực; chỉ bỏ transaction. Route khác làm I/O chậm (T2.9 gọi AI) cũng phải dùng transaction ngắn.
- `req.ip` ghi vào audit chưa có `trust proxy`: sau Caddy (M4) sẽ là IP proxy.
